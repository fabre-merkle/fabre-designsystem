# skill-tokens-studio

Drives the **Tokens Studio MCP** and **CLI** to manage a scaffolded project's token pipeline.
This skill is the authoritative agent runbook for every Tokens Studio operation in this project.

## Preflight

Before any section: verify prerequisites.

1. **Tokens Studio MCP available?** Probe for MCP tools containing `tokens_batch_create` or
   `set_project`. If absent: stop and show remediation — "The Tokens Studio MCP is not configured.
   The scaffold merges the `tokens-studio` entry into `.mcp.json` (Claude Code) or `.vscode/mcp.json` (VS Code) when an editor MCP item was selected; check the entry exists there and that the client has signed in (Claude Code: `/mcp`).
   See `packages/tokens/TOKENS-STUDIO.md` → 'MCP' for setup steps."
2. **CLI installed?** Studio-dependent `tokens:*` commands bootstrap it automatically when absent.
   Run `bun --cwd packages/tokens ./scripts/setup.ts` only to preinstall or diagnose it. Never add it
   to `trustedDependencies`: the pinned devDep + safe bootstrap avoid the Vercel EXDEV failure.
3. **DTCG present?** Check that `packages/tokens/dtcg/` exists and is non-empty. If absent, run
   `cd packages/tokens && bun scripts/setup.ts && ./node_modules/.bin/studio pull raw`.
   This invokes the CLI v2 `raw` output recipe and updates the local DTCG files from Studio.

## Initial project push

Push this project's tokens to a Tokens Studio project for the first time. Run this once, right after
the project is scaffolded, before any token edits.

> **This section is the agent prompt** shown on the scaffold completion screen and in the project
> README. Start here unless the user explicitly asks for a different section.

### Overview

1. Run the prepare helper to flatten DTCG → chunked payloads + export configs (deterministic, no network).
2. Create (or select) a Tokens Studio project via MCP.
3. Push all token chunks via the MCP `tokens_batch_create` tool.
4. Create theme groups + options from `$themes.json` via the MCP `themes` tool.
5. Confirm the generated CLI v2 `.studio.json` matches the selected project and ref.
6. Run `tokens:studio:exports` to create and run the CSS export presets.
7. Commit `.studio.json` and `.studio-push/` and tell the user to approve changes in Studio.

### Step 0 — Prepare (deterministic, no network)

```bash
bun --cwd packages/tokens ./scripts/studio-push-prepare.ts
```

This runs `studio-push-prepare.ts` from `packages/tokens/`. It:
- Flattens all `packages/tokens/dtcg/*.json` to `{token_set_name, name, type, value}` records.
- Chunks them into `.studio-push/chunks/chunk-NNN.json` (≤200 tokens each, the MCP limit).
- Reads `packages/tokens/dtcg/$themes.json` → `.studio-push/themes.json`.
- Emits `.studio-push/exports/css.json` (always).
- The split `css` export writes one file per set. When Fumadocs or Storefront bridge files are
  present, `tokens:studio:exports` applies their required local post-export transforms.

Check the summary output: note chunk count, token count, and which export configs were emitted.

### Step 1 — Create or select the Tokens Studio project

First inspect `packages/tokens/.studio.json` for an existing project and source ref. Confirm its
identity through a read-only MCP request before proposing changes. Do not create a replacement
project on a rerun. If no valid project is configured, ask once whether to create a new project or use an existing project ID. Do not create or import
anything until the user confirms that choice. On a rerun, first compare the prepared token count to
the selected project's token count. If tokens already exist, stop and ask the user to choose an
explicit update/replace flow; never create duplicate tokens by default.

**Create new:**

```
set_organization → list_projects (check if one already exists for this repo) →
  if new: create_project(name=<repo-name>)  ← use the repo root dir name
  if existing: set_project(project_id=<existing-id>)
```

Record the project ID — you'll need it in Step 5.

**If the user provides an existing project ID**, use `set_project` with that ID and skip `create_project`.

### Step 2 — Push token chunks

Read each chunk from `.studio-push/chunks/` in numeric sequence and call
`tokens_batch_create` with each. Each batch must remain within the MCP's 200-record limit. The
prepare step writes token records in dependency-safe tiers
(`foundation → brand → theme → semantic-web → web → semantic-fumadocs → semantic-storefront →
component`) and preserves `$metadata.json` `tokenSetOrder` within each tier. Do not reorder chunks
or their records lexically:

```
for each chunk file in .studio-push/chunks/ (chunk-001.json, chunk-002.json, ...):
  tokens_batch_create(tokens: <chunk contents>)
```

After each call, check the response for errors. If a batch partially fails, note which
`token_set_name` values failed and retry those tokens. Common failure: a reference token whose
`$value` is `{some.other.token}` pushed before the target set. Within each dependency tier, treat
`$metadata.json` `tokenSetOrder` as authoritative; in particular, keep
`semantic-fumadocs/color` followed by `semantic-storefront/color`,
`semantic-storefront/dimension`, `semantic-storefront/typography`, and
`semantic-storefront/opacity`.

After the final batch, verify the response totals match `.studio-push/summary.json`. If the count
does not match, stop and report the failed batch names; do not proceed to theme creation.

### Step 3 — Create theme groups and options

Read `.studio-push/themes.json` (the raw `$themes.json` array). Each entry has:
- `name` — the option name (e.g. `"default"`, `"brand-2"`, `"light"`)
- `group` — the theme group name (e.g. `"foundation"`, `"brand"`, `"theme"`)
- `selectedTokenSets` — map of `token_set_name → "enabled" | "source" | "disabled"`

Group entries by `group`, then for each group:

```
themes(action: "create_group", name: <group-name>)
for each option in the group:
  themes(action: "create_option",
         theme_group_id: <group-name>,
         name: <option-name>,
         selected_token_sets: [
           { name: <set-name>, status: <enabled|source|disabled> },
           ...  (only include entries where status != "disabled")
         ])
```

The `semantic-fumadocs` group (if present) must be created so the split CSS export resolves it.

### Step 4 — Wire the generated `.studio.json` with the real project ID

Keep the scaffolded `packages/tokens/.studio.json` shape. Replace `PROJECT_UUID` in
`source.project` with the selected UUID only if it is still a placeholder. If the file
already specifies that UUID, leave it and its authored outputs intact. If it specifies a
different project or ref, stop and report the mismatch; do not run `studio init --force`
or replace the user's configuration. Run `studio check --json` from `packages/tokens`.
The generated recipe has this structure:

```json
{
  "version": 2,
  "host": "https://api-production.tokens.studio",
  "source": { "project": "<project-id>", "ref": { "type": "branch", "name": "main" } },
  "outputs": {
    "raw": { "format": "raw", "dir": "dtcg" },
    "css": { "format": "css", "dir": "css", "options": { "fileLayout": "split" } }
  }
}
```

The displayed CSS options are abbreviated; preserve the full generated options and any
additional authored outputs/assets.

### Step 5 — Create and run CSS exports

```bash
bun --cwd packages/tokens ./scripts/setup.ts && bun --cwd packages/tokens ./scripts/studio-exports-setup.ts
```

This runs `studio-exports-setup.ts`: for each config in `.studio-push/exports/`, it calls
`studio exports create --name <name> --format css --config-file <file>`
then `studio exports run <name> --out ./css/` using the default v2 source.

Auth: if `TOKENS_STUDIO_TOKEN` is set it's used non-interactively; otherwise the CLI uses the
keychain session from `studio auth login`.

Expected outputs:
- `packages/tokens/css/` — the split CSS cascade (foundation, brand, theme, semantic-web, web layers).
- `packages/tokens/css/semantic-fumadocs/theme.css` — the `@theme {}` block for Fumadocs (only if
  the Fumadocs bridge is installed).
- `packages/tokens/css/semantic-storefront/default.css` — plain `:root {}` runtime source variables
  for Storefront Next (only if the Storefront bridge is installed).

### Step 6 — Commit and tell the user to approve

```bash
git add packages/tokens/.studio.json packages/tokens/css/ .studio-push/
git commit -m "chore: wire Tokens Studio project and push initial tokens"
```

Tell the user: **"Open Tokens Studio and approve the pending changes in the Studio UI
(Changes → Review → Approve). The tokens are staged in an agent workspace and only
land on the main branch after your approval."**

### Storefront Next dependency contract

When the project includes the Storefront token bridge, the push order must include the
`semantic-storefront` sets and the `semantic-storefront / default` theme group:

1. All eight `semantic-storefront/*` DTCG sets are present in the chunks and pushed in Step 2:
   `colors`, `radius`, `font`, `header`, `sidebar`, `agentic`, `custom`, and `typography`.
   Preserve `$metadata.json` `tokenSetOrder` rather than lexically sorting the sets.
2. The `semantic-storefront` **theme group** is created in Step 3 with option `"default"` and
   all eight sets enabled.
3. The shared split `css` export runs in Step 5 and the Storefront post-export transform emits
   `packages/tokens/css/semantic-storefront/default.css` — a plain `:root {}` block of bare source
   vars (`--background`, `--primary`, `--ui-radius`, `--font-sans`, …).
4. The consumer imports the self-contained bundle `packages/tokens/css/storefront/default.css`
   (rebuilt by `bun run tokens:studio:exports`) after `tailwind.css` and before `base.css` — never
   `semantic-storefront/default.css` on its own: its typography aliases `var(--brand-typography-*)`,
   which only the bundle defines.

**Storefront Next Figma sync** is intentionally manual via the Companion plugin (programmatic
Studio→Figma push stays parked). To sync:
1. Open the Storefront Next Figma file.
2. Install the **Companion for Tokens Studio** plugin.
3. Point it at the `semantic-storefront` set in this project's Studio project.
4. Pull → a matching variable collection is created / updated in the Figma file.

**If the Storefront bridge export fails**, check: (a) all `semantic-storefront/*` sets were pushed
without errors; (b) the `semantic-storefront` theme group exists with option `"default"` and every
set enabled; (c) `packages/tokens/css/semantic-storefront/default.css` exists before running
`bun run tokens:studio:exports`.

### Fumadocs dependency contract

The `semantic-fumadocs` split CSS export resolves **only** in this order:

1. The full cascade (`foundation → brand → theme → semantic-web`) is pushed (Step 2).
2. The `semantic-fumadocs` **theme group** exists on the project (Step 3).
3. The shared `css` export and Fumadocs post-export transform run (Step 5).
4. The docs app imports `packages/tokens/css/semantic-fumadocs/theme.css` in its `app/globals.css`.

The `semantic-fumadocs` token set is 100% references into the rest of the cascade — for example:

| fd token | resolves to |
|---|---|
| `color.fd.accent` | `{theme.color.secondary.9}` |
| `color.fd.background` | `{theme.color.neutral.1}` |
| `color.fd.diff-add` | `{theme.color.utility.success.3}` |
| `color.fd.accent-foreground` | `{foundation.color.whiteAlpha.100}` |

**If the Fumadocs export fails**, check: (a) the full cascade was pushed without errors; (b) the
`semantic-fumadocs` theme group exists and has the correct `selectedTokenSets` wired; (c) the
shared `css` export completed before the post-export transform ran.

## Re-pull tokens (update local CSS from Studio)

After editing tokens in the Studio UI and merging changes on the main branch:

```bash
# Re-run the shared split export and integration post-export transforms:
bun run tokens:studio:exports
```

For non-interactive / CI use, set `TOKENS_STUDIO_TOKEN` in `.env`.

---

## Refresh CLI config

If the project ID or ref changes, update `source` intentionally and run `studio check --json`.
Keep existing output recipes/assets; do not re-run `studio init` over a valid config.

## Add Tokens Studio to an existing project

If the project was initially scaffolded WITHOUT tokens-studio and you want to add it:

1. Check this design system's registry documentation for an available Tokens Studio integration.
   Use its published namespace and discovered item name; if none is published, ask the system
   maintainer to provision the integration rather than installing an unrelated upstream item.
2. Run any Studio-dependent `tokens:*` command; it installs the CLI binary on demand.
3. Follow the **Initial project push** section above.
