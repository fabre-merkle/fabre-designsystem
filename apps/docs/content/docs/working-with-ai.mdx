## Start with context

Ask your agent to read `AGENTS.md`, the relevant guidance and a matching skill before editing. Describe the interface you want, its constraints and what a successful result looks like.
`AGENTS.md` explains how the project is built.
Read the matching `DESIGN.md` context before design or styling work.
Use current project sources rather than pasted excerpts. Configuration alone does not mean a tool is authenticated or ready.
{/* topic:end ai-entry-points */}

{/* topic:start ai-workflow */}
## Work on a change

<Steps>
<Step>
### Establish the task
Agree on the outcome, the files in scope and how the result will be checked.
</Step>
<Step>
### Reuse and implement
Reuse installed components and their supported variants before creating new ones.
Use semantic tokens and follow the owning documentation.
</Step>
<Step>
### Review the evidence
Run the affected checks and inspect the interface, including keyboard use, narrow layouts and reduced motion. Review the diff before accepting changes; passing checks are not approval.
</Step>
</Steps>

## Keep guidance current

The topic map in `.agents/documentation-topics.json` identifies each selected topic's owning page. Link to that owner rather than maintaining competing copies.
Fillable sections retain `topic:start` and `topic:end` markers. Preserve both markers and leave unsupported topics at their existing baseline.
When an approved change affects documented behaviour, use the guideline-update skill to update the owning page. Preserve topic markers and link to that page instead of duplicating guidance.
After token changes, regenerate DESIGN.md from current token data rather than hand-editing its generated references.
